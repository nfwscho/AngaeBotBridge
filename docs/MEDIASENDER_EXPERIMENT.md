# MediaSender 기반 앙개봇 카카오톡 직접 공유 실험

## 2026-11-07 — PNG 직접전송 엔진 v0.4.25 / Python Core v0.7.6

### 개발한 내용
- 기존 A/B 실험 코드는 그대로 유지하고 **독립된 `②-B-2 PNG 직접전송`** 기능을 추가. S20+에서 사용자 물리 승인과 독립 ON 스위치가 필요하며 **기본 OFF**.
- 실험에서 검증된 개인 1:1 대화방 **표시방 이름=발신자 이름=알림 tag 조합** 하나만 연결. 카카오 명령으로 자동 등록되거나 다른 방/단톡방에 적용되지 않음.
- Android 액션 `앙개야 이미지 직접시험`: 매번 새로운 20자리 랜덤 파일명/Content URI를 갖는 검증 가능한 **DIRECT PNG** 테스트 사진을 공유.
- Android 액션 `앙개야 이미지 직접차트 MU` 또는 `... 직접차트 005930`: 토큰으로 인증된 같은 S20+의 Python Core `GET /v1/media/stock-chart?symbol=<ticker>`를 호출하고 실제 검증된 일봉 종가로 **720×420 RGB PNG** 생성. 공개 시장 종목만 허용. 명확한 차트 데이터 실패면 가짜 가격으로 그리지 않고 거부.
- Python Core PNG는 Pillow·Matplotlib 없이 표준 라이브러리로 생성하여 Termux 의존성/기존 설치 데이터에 영향 없음. HTTP 응답은 `image/png`, `Cache-Control: no-store`, 토큰 인증 필수.
- Android Bridge는 PNG 전체 청크 CRC, IHDR 크기·색상모드, 최대 1.2MB, 원본 localhost 주소만 검증. 사용자가 임의 파일 경로나 외부 URL을 보내는 명령은 지원하지 않음.
- ContentProvider는 오직 앱 자체 이미지 캐시에서 테스트 PNG, A/B PNG, 엄격한 UUID 파일명 PNG만 **읽기 전용**으로 제공. 카카오톡 이미지 미리보기를 위해 `OpenableColumns.DISPLAY_NAME`/`SIZE` 제공.
- 카카오톡 직접 공유 Intent는 A 실기기에서 확인한 `key_id`, `key_type=1`, `key_from_direct_share=true` 조합 사용. 접근성 서비스는 새 직접 PNG 엔진에서 **수신자 선택/보내기 버튼을 자동 클릭하지 않음**. `DIRECT_PNG_INTENT_REQUESTED`는 전송 요청 로그이지 서버 수신 보증이 아님.
- 기존 `앙개야 이미지 자동시험`, `직공유경로확인`/A-B, `직공유시험`/기존 접근성 클릭, 텍스트 답장, 주식·부동산·메모·날씨·개인 할 일, 운영 로그/UI/DB/.env/토큰·잠금 정책은 모두 유지.

### S20+ 실제 시험 (최신 기능 브랜치 배포 후에만)
1. Windows에서 기존 `deploy-angaebot.ps1 -Branch "feature/mediasender-experiment-20261107" -InstallAndroid -WaitMinutes 12` 명령으로 Core와 Android 앱을 배포한다. 배포 스크립트는 정확한 SHA에 대한 GitHub Actions 전체 성공을 요구한다.
2. S20+ 앙개봇 Bridge의 **②-B 이미지 자동전송** 스위치는 기존처럼 ON, 접근성 서비스 연결 확인. 기존 **②-B-1 MediaSender A/B 실험**은 OFF여도 새 엔진에서 동작한다.
3. S25 본인 1:1 방에서 `앙개야 이미지 직공유진단` 전송.
4. **5분 안에 S20+ 앱 ②-B-2**에서 `진단된 1:1 대상 연결 승인` 버튼을 직접 누른 뒤 표시된 방/발신자/마스킹 ID를 확인하고 승인. 타인/단체방/이름 불일치 후보는 허용하지 않는다.
5. S20+의 `검증된 1:1 PNG 직접전송 허용` 스위치를 ON으로 설정하고 **직접 PNG 전송 설정 저장** 버튼을 누른다.
6. S25에서 `앙개야 이미지 직접시험`을 전송한다. 앱은 새로운 `DIRECT PNG` 표식의 사진을 공유 요청한다. 원본 사진 말풍선 및 흰색 썸네일 현상 여부를 확인한다.
7. 실제 PNG가 도착했으면 S25에서 `앙개야 이미지 직접차트 MU` (또는 `... 직접차트 005930`) 전송한다. Python 엔진이 실제 거래일/종가 데이터로 만든 PNG 차트를 전송하는지 확인한다.
8. 로그 `DIRECT_PNG_PAIR_APPROVED`, `DIRECT_PNG_SETTING_SAVED`, `DIRECT_PNG_QUEUED`, `DIRECT_PNG_INTENT_REQUESTED`, `DIRECT_PNG_RECEIPT_UNCONFIRMED` 및 Python `MEDIA_STOCK_CHART_READY/FAILED` 확인. 마지막 로그는 수신 성공 보증이 아니라 관찰 종료다.
9. 의도하지 않은 창/대상/전송이 보이면 즉시 **②-B-2 직접 PNG 스위치를 OFF 저장**하고 로그를 확인한다. 연결 해제는 기존 DB·로그·설정을 삭제하지 않는다. 구형 방식 비교는 `앙개야 이미지 자동시험` 사용.

### 제한과 안정화 조건
- 현재 실제 작동이 증명된 것은 S20+ 본인의 **1:1 방 한 곳**이다. 다른 채팅방, 다중 수신자, 카카오톡 버전, MP4 동영상은 새 엔진에서 **아직 지원하거나 검증하지 않았다**.
- 카카오 알림 tag는 공식 안정 ID가 아니다. 사용자가 S20+에서 검증된 후보만 직접 승인하고 매 요청의 태그/방/발신자를 다시 비교한다. 방 표시 이름이 바뀌면 연결을 끊고 다시 승인해야 한다.
- 카카오톡 Intent 자체의 비공식 내부 처리에 의존한다. Intent 시작/타임아웃 로그만으로 실제 카카오톡 서버 전달을 확정하지 않는다.
- PIN·패턴·비밀번호 인증 잠금은 기존대로 **거부**하며 잠금 우회·비밀번호 보관을 하지 않는다.
- 고유 Content URI와 파일 이름·크기 메타데이터를 제공했지만 **흰색 썸네일 해결은 S20+ 실기기에서 추가 확인 필요**.
- 실제 Core 차트 엔드포인트에는 사용자별 그룹 별칭이나 임의 URL·파일 접근을 허용하지 않는다. 무료 시세의 오류/지연은 원래 데이터 공급자 정책을 따르며 잘못된 가격을 만들어내지 않는다.

### 실험 결론과 남은 한계
- 동일한 1:1 방에서 **세 가지 카카오톡 직접 공유 Intent extra의 존재 여부를 변경한 결과만으로 전송 동작이 달라졌음**을 실기기로 확인했다. 현재 카카오톡 버전에서는 이 **조합이 수신자 선택을 건너뛰고 PNG를 전송하는 데 실질적인 역할을 한다**는 강한 증거다.
- 현재 검증한 대상은 숫자형 알림 tag와 수신 채팅이 대응하는 **본인의 1:1 방 1곳**뿐이다. 알림 `StatusBarNotification.tag`가 일반적으로 안정적인 `channelId`라는 사실이나 다른 친구·단톡방에도 동일하게 적용된다는 사실까지 증명하지 않는다.
- `key_id` 단독의 필요성은 미확인이다. A는 **3개 키를 한꺼번에 포함**, B는 한꺼번에 제외했으므로 세 키 중 어느 것이 필수인지 별도 실험 없이는 결론 낼 수 없다.
- `MEDIA_DIRECT_PROBE_TIMEOUT`은 접근성 UI 식별·관찰 제한시간 도달을 의미한다. A 사진이 실제 수신된 사실을 부정하지 않으며, 앱이 서버 수신을 확인한다는 뜻도 아니다.
- `IMAGE_WAKE_DISMISSED`는 **사용자 인증이 필요하지 않은 잠금** 해제 성공이다. PIN·패턴·비밀번호가 필요한 상태에서의 이미지 전송은 아직 검증하지 않았고 기존 구현은 이를 거부한다.
- `REPLY_REQUESTED`는 카카오 알림 RemoteInput 텍스트 응답 **요청** 기록이지 사진 수신 확인이 아니다. 서비스 로그의 `room= / sender=` 공란도 자동 이미지 서비스가 해당 값을 로그 인자로 전달하지 않는 표시이며 허용목록 실패의 증거는 아니다.

### 이후 개발 우선순위
1. 신규 **독립 OFF 기본값의 직접 PNG 전송 엔진**을 기존 UI 이미지 자동전송과 분리해 단일 허용 1:1 방에서 반복·재시작 테스트. 기존 성공 경로를 덮어쓰지 않는다.
2. 실제 전송 성공과 단순 Intent 시작을 구별하는 상태/로그를 개선하되, 서버 수신 확인을 증명하지 못하면 `전송 요청`으로만 표시한다.
3. PNG 썸네일이 흰색으로 나왔으나 원본은 정상인 현상을 캐시/썸네일/URI 관점에서 별도로 재현·개선한다.
4. MP4 동영상·다중 파일 기능은 직접 공유 PNG 안정화 후, 실험용 안전한 고정 파일로 지원 여부를 단계별 검증한다.
5. PIN이 실제 인증을 요구하는 상태의 전송은 별도 설계가 필요하며 잠금 우회 구현 없이 보안 정책을 유지한다.

## 2026-11-07 실기기 로그 판정과 A/B 대조 (Android v0.4.24)

- S20+ 21:08:54 `MEDIA_DIRECT_PROBE_STARTED`, `MEDIA_DIRECT_INTENT_STARTED`가 확인되고, 21:08:55/58 및 21:09:04 `MEDIA_DIRECT_PROBE_WAIT`, 21:09:14 `MEDIA_DIRECT_PROBE_TIMEOUT`이 확인됐다.
- `pickerHeading=true targetNameVisible=true roomChoices=0 sendButtons=0 autoClick=false`는 공유 화면 요소를 완전히 분류하지 못했다는 뜻이다. **타임아웃을 사진 전송 실패로 해석하지 않는다.** 사용자 화면에는 같은 분에 사진 말풍선이 나타났으나 이번 명령으로 새로 발송된 사진인지 아직 별도 증명이 필요하다.
- A/B 실험은 기존과 같은 테스트 PNG를 재사용하는 오류를 없앤다. 실제 발송 원인을 수신 사진 내부의 A/B 표식으로 구분한다.

**A — 직접 공유 힌트 포함:**
1. S20+ MediaSender 실험 스위치와 기존 이미지 자동 스위치 ON, 1:1 테스트 방 허용목록 확인.
2. S25에서 `앙개야 이미지 직공유진단` → 5분 내 `앙개야 이미지 직공유경로확인` 순서.
3. 앱은 A 전용 PNG(`A: DIRECT (KEY_ID)`)와 `key_id`, `key_type`, `key_from_direct_share`를 카카오톡 공유 Intent에 넣는다. 방 선택/보내기 버튼을 **자동 클릭하지 않는다.**
4. S25의 같은 방에 **A 문구가 새겨진 사진**이 새로 도착하는지 확인. 뜬 카카오톡 화면은 수동으로 전송 버튼을 누르지 말고 관찰한 후 닫는다.

**B — 직접 공유 힌트 제외:**
1. A 시험 화면을 닫고 다시 `앙개야 이미지 직공유진단`을 보낸다. 승인 토큰은 매번 1회 사용 후 폐기되므로 반드시 재진단한다.
2. 5분 이내 `앙개야 이미지 직공유대조` 입력.
3. 앱은 B 전용 PNG(`B: CONTROL (NO KEY_ID)`)를 만들고 A와 동일한 Intent 형식·플래그·관찰 모드로 공유하되 **채팅방 직접 지정 extra 3개를 넣지 않는다**.
4. 자동 버튼 클릭은 없지만 카카오톡 자체의 발송을 막지 않으므로, S25에 B 사진이 새로 도착했는지 반드시 확인한다.

**판정**: A만 수신되고 B는 수신되지 않으면 `key_id` 등 힌트의 효과를 지지한다. A와 B가 모두 수신되면 ID 없이도 가능한 다른 전송 경로이므로 직접 지정 효과를 확정하지 않는다. 둘 다 수신되지 않으면 미확인. 수신 여부뿐 아니라 `MEDIA_DIRECT_PROBE_STARTED`, `MEDIA_DIRECT_INTENT_STARTED`(A), `MEDIA_DIRECT_CONTROL_INTENT_STARTED`(B), `MEDIA_DIRECT_PROBE_RESULT`/TIMEOUT, `IMAGE_UI_ROOM_SELECTED`, `IMAGE_UI_SEND_REQUESTED` 등의 로그도 함께 확인한다.

**주의**: 이 실험은 공식 메시지 API가 아니며 카카오톡 내부 공유 동작을 활용한다. 앱 자체 자동 클릭은 차단하지만, Android Intent를 받은 카카오톡이 자동 발송하는 경우까지 막지는 못한다. 반드시 본인과의 1:1 시험 방에서만 진행하며 PIN 인증 잠금 정책은 기존 그대로 유지한다. **본인과의 실기기 결과가 확정되기 전에는 다른 대화방에 사용하지 않는다.**


## 목적
- 공개 소스 https://github.com/hehee9/mediaSender 의 Android 공유 Intent 설계에서 직접 채팅방 선택 아이디어만 참고한다.
- 별도 메신저봇R 설치 없이 앙개봇 Android Bridge 안에서 채팅방 ID 후보를 진단한다.
- MediaSender 원본 JavaScript는 복제하지 않는다. 참고한 세 Intent extra는 key_id, key_type, key_from_direct_share이다.
- 해당 값은 공식 카카오 메시지 API가 아니고 내부 공유 형식에 종속적이므로 카카오톡 업데이트에 따라 바뀔 수 있다.

## S20+ 안전 시험 절차
1. 기존 앙개봇 1:1 카카오톡 및 호출어·방/발신자 허용목록이 정상인지 확인한다. `앙개야 이미지 자동시험`이 작동하는 기존 경로는 그대로 유지한다.
2. S25에서 `앙개야 이미지 직공유진단` 전송. S20+는 알림 tag가 숫자 8~18자리인지, room과 sender가 정확히 같은지 검사한다. 성공 시 자릿수 및 끝 네 자리만 응답하고 5분짜리 일회성 메모리 승인을 남긴다. **진단 단계에서는 어떤 파일도 전송하지 않는다.**
3. S20+ Android Bridge의 ②-B-1 MediaSender 직공유 실험 스위치를 ON으로 하고 저장한다. 기존 ②-B 이미지 자동전송 스위치 및 접근성 서비스도 ON이어야 한다.
4. **권장 2차 검증**: 5분 내 S25에서 `앙개야 이미지 직공유경로확인`을 전송한다. 이 명령은 MediaSender의 direct-share 힌트로 카카오 공유 화면을 열지만 **수신 방 선택이나 보내기 버튼을 자동 클릭하지 않는다.** S20+에서 어떤 화면이 보이는지 직접 확인하고 건드리지 않는다. Android에서 다른 앱의 공유 처리 자체가 자동으로 진행되는 경우까지 강제로 금지하지는 못한다.
5. 로그 `MEDIA_DIRECT_PROBE_RESULT`의 `route=RECIPIENT_PICKER`라면 수신자 선택창이 표시되어 직접 지정 효과가 확인되지 않은 것. `TARGET_SCREEN_CANDIDATE`는 대상 텍스트/버튼이 함께 보이는 후보일 뿐 정확한 ID 또는 실제 발송 성공을 증명하지 않는다. `MEDIA_DIRECT_PROBE_WAIT`·`MEDIA_DIRECT_PROBE_TIMEOUT`이면 판단 보류. 화면에서는 자동 클릭 없이 20초까지 관찰한다.
6. 이전 실험의 `앙개야 이미지 직공유시험`은 기존 접근성 자동화의 방 선택·보내기 클릭을 **그대로 사용**한다. 사진이 도착해도 직접 채팅방 ID 동작을 입증하지 못한다. `MEDIA_DIRECT_FALLBACK_ROOM_CLICK` / `IMAGE_UI_ROOM_SELECTED`이 있으면 기존 방식으로 채팅방을 선택한 것.
7. 관찰용 화면을 닫은 후 반드시 새로운 `앙개야 이미지 직공유진단`을 먼저 보내야 한다. 진단 승인은 1회용이며 소모되면 재사용할 수 없다. 기존 사진 자동전송을 비교하려면 `앙개야 이미지 자동시험`을 사용한다. 부작용이 있으면 실험 스위치를 OFF 한다.
8. 이벤트 로그 `MEDIA_DIRECT_CANDIDATE`, `MEDIA_DIRECT_PROBE_QUEUED`, `MEDIA_DIRECT_INTENT_STARTED`, `MEDIA_DIRECT_PROBE_RESULT` 또는 `MEDIA_DIRECT_PROBE_TIMEOUT`을 확인한다. Intent 시작 성공은 실제 수신 확인이 아니다.

## 한계·안전
- Android StatusBarNotification.tag는 **알림 태그**일 뿐 실제 카카오톡 채팅방 ID인지 보증되지 않는다. 숫자가 보인다는 사실만으로는 직접 발송 성공 또는 올바른 대상 인증을 뜻하지 않는다.
- PIN·패턴·비밀번호 인증 잠금은 기존과 같이 거부한다. 화면 잠금 우회/비밀번호 입력 기능은 없다.
- 채팅방 표시 이름==발신자 표시 이름일 때만 개인 1:1 시험 후보로 처리한다. 단톡방 및 표시 이름 불일치 방에서는 거부한다. 이름만으로 계정 신원을 강하게 보증할 수는 없다.
- 별도 스위치 OFF가 초기값이고 기존 접근성 이미지 자동전송·텍스트 빠른답장 경로를 대체하지 않는다. 위험을 고려하여 의도한 테스트용 계정·방에서만 실행한다.
- 실험에는 내부 생성 PNG만 사용한다. 동영상/외부 URL/다중 파일은 이번 첫 단계에 도입하지 않고 채팅방 지정 자체를 검증한 다음 추가한다.
- 테스트 또는 직접 공유 요청이 오류 없이 반환됐다는 사실은 카카오톡 서버 업로드 완료나 상대방 수신의 증거가 아니다.
- 기존 DB, SQLite 로그, Python Core, 배터리 응답, Android Bridge 설정·UI, .env와 채팅 내용은 삭제하거나 초기화하지 않는다.
